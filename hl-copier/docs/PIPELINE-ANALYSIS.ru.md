# hl-copier — разбор архитектуры пайплайна: задержки и устойчивость

> Снимок на 2026-06-15. Замеры латентности сделаны **на боевом Pi** (домашний интернет → серверы бирж в US). На другом канале/VPS числа будут другими.

## TL;DR
- Пайплайн копирования **простой и линейный**: событие цели (HL) → пересчёт → ордера на Binance.
- **Реальная задержка event→ордер ≈ 5.7 сек** (замерено). Из них: дебаунс 1.2с + цепочка из 7 последовательных REST ≈ 3.9с + отправка ордера ≈ 0.6с.
- **Узкое место — последовательные REST-вызовы** в `_compute` (network-bound с домашнего Pi), а не логика.
- Вывод: текущая архитектура хороша для **медленных свингеров** (сделки раз в минуты/часы), но не для скальперов (сделка каждые ~3.6с — мы опаздываем).
- Снизить до **~1.5–1.8с не уезжая с Pi** реально (параллелизм + кэш + дебаунс). До **~0.3–0.4с** — только VPS рядом с биржей.

## 1. Карта компонентов

```
copier/
  hl/rest.py      HLInfo        — чтение Hyperliquid (REST). Глобальный троттл + ретрай на 429.
  hl/ws.py        FillStream    — устойчивый WS на userFills (авто-реконнект + watchdog + ресабскрайб).
  core/positions  net_positions, account_value, price_move_pct — чистые расчёты по стейту HL.
  core/plan.py    compute_plan  — желаемые net-позиции: плечо (fixed/mirror), заморозка плюсовых
                                   на старте, кэпы (плечо, ноционал/монета). Чистая функция.
  core/sizing.py  desired_mirror/diff_orders — АЛЬТЕРНАТИВНЫЕ чистые помощники (в горячем пути
                                   НЕ используются; кандидат на чистку/слияние с plan).
  execution/
    binance.py    BinanceFutures — исполнение на Binance USDT-M (REST): account/positions/
                                   mark_prices/funding/leverage/market_order/user_trades.
    executor.py   build_orders / build_orders_hedge — diff желаемое↔текущее → список ордеров
                                   (one-way и hedge). apply() — отправка. Чистые + apply.
server/
  controller.py   Controller    — ЕДИНСТВЕННЫЙ, кто торгует. Циклы копира (poll/ws), монитор-WS-
                                   алерты, статус/services, аудит, Telegram, карточки трейдеров.
  api.py          REST/статика фронта.
tools/serve.py    запуск веб-интерфейса (systemd-сервис hl-copier на Pi).
```

Торгует и держит состояние **только `Controller`** (синглтон). Всё остальное — чистые функции или тонкие клиенты.

## 2. Пайплайн копирования (горячий путь)

Два режима, переключаются `data_mode` (poll | ws):

### WS-режим (сейчас в проде)
```
[Цель торгует на HL]
      │  HL WS push (userFills)
      ▼
FillStream.cb → on_fill → self._wake.set()          ← мгновенно
      │
      ▼
_ws_reconcile_loop:
   wake.wait() → time.sleep(1.2)  ← ДЕБАУНС 1.2с (батчим серию филлов)
      │
      ▼
_compute(do_apply=live):
   1) hl.all_mids()                 ~0.61с  REST
   2) hl.clearinghouse_state(цель)  ~0.39с  REST
   3) bn.account()                  ~0.87с  REST
   4) bn.positions()                ~0.66с  REST
   5) bn.funding_rates()            ~0.48с  REST   (нужно только UI!)
   6) bn.position_mode()            ~0.37с  REST   (почти не меняется)
   ──────────────────────────────── compute_plan() — чистая, ~0мс
   7) bn.mark_prices()              ~0.48с  REST
   ──────────────────────────────── build_orders() — чистая, ~0мс
   8) executor.apply():
        set_leverage (если надо)    REST
        market_order × N            ~0.64с/ордер  REST  ← ОРДЕР УШЁЛ
   9) bn.positions_detail()         REST   (обновить UI после исполнения)
   10) статус + services + heartbeat
```
**Фолбэк:** если за 60с не было ни одного WS-события — `_ws_reconcile_loop` всё равно делает `_compute` (страховка). При обрыве WS — `on_reconnect` будит немедленный реконсайл (догон пропусков).

### Poll-режим
То же `_compute`, но вызывается по таймеру `poll_interval_sec` (30с), без WS. Проще, но задержка до 30с.

### Что делает `_compute` по сути
1. Узнать **желаемые** позиции = масштаб экспозиции цели под наш эквити (`compute_plan`): `notional[coin] += szi · mark · (sleeve / target_value)`, затем кэпы (плечо, ноционал/монета), заморозка плюсовых на старте.
2. Узнать **текущие** наши позиции (Binance).
3. `executor.build_orders` — diff желаемое↔текущее → маркет-ордера (с `reduceOnly` на сокращение/закрытие), фильтр по `minQty/step/minNotional`.
4. `apply` — выставить плечо + маркет-ордера.

Реконсиляция **идемпотентна**: всегда сводим к целевой net-позиции, поэтому пропущенное событие «самозалечивается» на следующем тике. Это плюс к устойчивости, но усиливает дрейф на минималках (см. §5).

## 3. Бюджет задержки (замер на Pi)

| Этап | Время | Природа |
|---|---:|---|
| Дебаунс `sleep(1.2)` | 1200 мс | заложен в коде (батчинг) |
| HL all_mids | 606 мс | сеть (Pi→US) |
| HL clearinghouse(цель) | 386 мс | сеть |
| BN account | 872 мс | сеть |
| BN positions | 656 мс | сеть |
| BN funding_rates | 480 мс | сеть · **только для UI** |
| BN position_mode | 373 мс | сеть · почти статика |
| BN mark_prices | 484 мс | сеть |
| Отправка ордера (BN POST) | ~640 мс | сеть |
| **ИТОГО event→ордер** | **≈ 5700 мс** | |

**Где время:** ~3.9с — это 7 REST-вызовов **подряд**, каждый ~0.4–0.9с из-за RTT с домашнего канала до бирж. Логика (compute_plan/build_orders) — единицы миллисекунд, она не виновата.

Скальпер `0x31dea…` делает ~1000 филлов/час (сделка каждые ~3.6с) → при нашей задержке 5.7с мы реагируем, когда он уже развернулся.

## 4. Что уже сделано для устойчивости (сильные стороны)
- **WS с авто-реконнектом** (`FillStream`): watchdog (поток жив + свежесть сообщений ловит half-open), пересоздание `Info` + ресабскрайб с backoff, `on_reconnect`-догон. SDK сам не реконнектится — мы это закрыли.
- **Троттл HL + ретрай на 429** (общий пейсер ~6–7/сек) — бёрсты не роняют статус.
- **Фолбэк-реконсиляция 60с** в ws-режиме + немедленный реконсайл после обрыва.
- **Идемпотентный реконсилятор** — пропуски самозалечиваются.
- **Заморозка плюсовых на старте** — не копируем чужой профит, открытый до нас.
- **Кэпы**: `leverage_cap`, `max_notional_per_coin`, фильтры `minQty/step/minNotional`.
- **Binance -1021** (recvWindow) — устойчивость к рассинхрону времени.

## 5. Слабые места / риски
1. **Задержка 5.7с** (см. §3) — последовательные REST + дебаунс.
2. **Дрейф на минималках**: наш эквити $566 ≪ счёта крупной цели → его микро-доливки масштабируются в `<$5 / меньше шага` → `skip` → наша позиция расходится с целевой. В логах пачки `$1 < minNotional $5`, `qty < minQty/step`. Остаток **нигде не копится** → дрейф постоянный.
3. **Маржа**: разово `-2019 Margin is insufficient` — нет буфера/предпроверки маржи перед ордером.
4. **Обрывы WS** часто (раз в 15–60 мин). Реконнект есть, но в окне обрыва события идут только из 60с-фолбэка → доп. задержка; филлы за окно прилетают снимком и проглатываются (по позиции догоняем реконсайлом).
5. **Тяжёлый `_compute` на каждое событие**: полный пересчёт всех символов + 7 REST, даже если изменилась одна монета. Часть данных почти статична (`funding_rates`, `position_mode`, фильтры).
6. **Только маркет-ордера** → тейкерская комиссия + проскальзывание (для частой торговли заметно).
7. **`sizing.py` дублирует `plan.py`** и в горячем пути не используется — мусор/риск расхождения.

## 6. Рекомендации

### A. Снижение задержки — дёшево, остаёмся на Pi (цель ~5.7с → ~1.5–1.8с)
1. **Параллелить REST-цепочку** (потоки/futures): HL-стейт + BN account/positions/marks тянуть разом → не сумма (3.9с), а самый медленный (~0.9с). **−~3с.**
2. **Убрать из горячего пути статику**: `funding_rates` (только UI) и `position_mode` (меняется ~никогда) — кэшировать раз в N минут / считать вне тика. **−~0.85с.**
3. **Снизить дебаунс** 1.2с → ~0.25с (или адаптивно: короче для редких событий). **−~0.95с.**
4. **`positions_detail` после ордера** — для UI, не блокировать им горячий путь (делать асинхронно).
5. **Замер латентности в логи**: писать `event_ts (филл) → order_sent_ts` на каждую копию — получить точные числа на след. сессии вместо оценок.

### B. Снижение задержки — инфраструктура (цель ~0.3–0.4с)
6. **Исполнение на VPS рядом с биржей** (напр. AWS Tokyo/ap-northeast — там Binance): RTT вызова ~0.5с → ~0.03с. Это единственный путь к «скальп-классу». Минус — уезжаем с домашней малины.
7. **Push вместо poll для своего счёта**: Binance **user-data stream (WS)** — позиции/баланс приходят сами, не дёргаем `account()/positions()` каждый тик.
8. **Инкрементальный таргет-стейт**: держать net-позицию цели из потока филлов (мы их и так получаем по WS), а не запрашивать `clearinghouse_state` каждый тик.

### C. Устойчивость / корректность исполнения
9. **Копить остаток ниже minNotional**: не отбрасывать суб-минимальные дельты, а накапливать и слать ордер, когда сумма перевалит $5/шаг — убирает дрейф.
10. **Буфер маржи + предпроверка** перед ордером (не загружаться под завязку) — против `-2019`.
11. **Гард свежести данных**: если стейт устарел (WS молчит, REST падает) — не исполнять по старому, помечать «stale».
12. **Лимитные/post-only ордера** для несрочных сведений — экономия на комиссии/проскальзывании.
13. **Чистка**: удалить неиспользуемый `sizing.py` или свести в `plan.py`.

## 7. Вывод и профиль цели
Архитектура — рабочая и понятная; основной долг — **латентность REST-цепочки** и **дрейф на минималках** при маленьком счёте.

**Кого копировать (под текущие возможности):**
- **медленные свинг/позиционные** трейдеры: вход/выход раз в часы–дни, держат позиции;
- немного активов, без HFT/MM;
- желательно сопоставимый порядок «крупности», чтобы движения не уходили в суб-минимальные у нас.

**Кого НЕ копировать:** скальперы/MM/квант-боты (мы медленнее на 5+ сек и теряем их edge; см. разбор `0xd4bb…` — BTC-MM).

**Порядок работ (рекомендую):** A1+A2+A3+A5 (параллелизм + кэш статики + дебаунс + замер) → проверить реальную задержку → при желании B6/B7 (VPS + user-stream) → C9/C10 (остаток + буфер маржи).
