# Ядро копира — как и когда работает

> Док по логике копирования HL → Binance: пропорция и риск, кэпы, реконсиляция, догон,
> скейл позиций, округления, baseline-заморозка, формат алертов и полный справочник настроек.
> Снимок на 2026-06-16. Связано с [PIPELINE-ANALYSIS.md](PIPELINE-ANALYSIS.md) (архитектура/задержки).

---

## 1. Модель в одну фразу
Копир **реконсиляционный, идемпотентный**: на каждом тике он смотрит «где мастер сейчас»
(net-позиции на Hyperliquid) и «где мы сейчас» (позиции на Binance), считает **желаемое**
состояние под наш эквити, и доводит нас к нему минимальными ордерами. Он **не повторяет
каждую сделку 1:1**, а постоянно сводит позицию к цели. Любое расхождение (пропуск события,
ручная правка, округление) самозалечивается на следующем тике.

```
Hyperliquid (мастер)            Наш расчёт                     Binance (мы)
  net-позиции цели  ──►  желаемое = пропорция под наш    ──►  diff-ордера
  (clearinghouse)        эквити  →  кэпы  →  заморозка         (market)
        ▲                                                        │
        └──────────── триггер реконсиляции ◄─────────────────────┘
            WS-филл цели · фолбэк 60с · реконнект · poll N сек
```

## 2. Пропорция и риск (главное)

### Как считается желаемый размер
Для каждой монеты:
```
желаемый_ноционал = ноционал_цели × (наш_эквити / эквити_цели) × вес_цели
```
То есть мы держим **ту же долю своего капитала**, что мастер держит от своего. Это «полный
риск мастера» — копируем его **эффективное плечо** (ноционал/эквити).

> Пример (pension): у мастера ETH-шорт $109M при эквити $19M → эфф. плечо **5.73×**.
> Наш эквити $566 → полная пропорция = 566 × 5.73 = **~$3 240 шорта** (тоже 5.73×).

### Когда мы ОГРАНИЧИВАЕМ риск (кэпы)
Три ограничителя ужимают желаемое (по порядку срабатывания):

| Настройка | Что делает | Пример (эквити $566) |
|---|---|---|
| `max_notional_per_coin_usd` | потолок **размера позиции по монете**, $ | $800 → ETH-шорт максимум $800 |
| `leverage_cap` | потолок **суммарного ноционала** = эквити × cap | 3 → весь портфель ≤ $1 698 |
| `mirror_max_leverage` / `fixed_leverage` | потолок **плеча ордера** на Binance | 100 → плечо мастера не режется |

Срабатывает **самый строгий**. В примере pension: пропорция $3 240 → режется `max_notional_per_coin`
до **$800** (1.41× нашего эквити) → мы держим ~25% от его риска.

### Полный риск vs ограниченный — как переключать
- **Ограниченный (по умолчанию, рекомендуется для мелкого счёта):** `max_notional_per_coin` и
  `leverage_cap` ниже пропорции → держим срез. Безопасно, но мельче мастера.
- **Полный риск мастера:** поднять ВСЕ три потолка выше пропорции:
  `max_notional_per_coin_usd` → очень большой; `leverage_cap` ≥ эфф. плечо мастера;
  плечо ордера ≥ эфф. плечо (иначе не хватит маржи: ноционал/плечо > эквити → `-2019`).
  ⚠️ На мелком счёте полный риск = почти вся маржа в одной позе, ликвидация близко,
  ликвиднут мастера — ликвиднут и нас.

### Плечо: mirror vs fixed
- `leverage_mode=mirror` → плечо ордера = `min(плечо_мастера, mirror_max_leverage)`.
- `leverage_mode=fixed` → всегда `fixed_leverage`.
- **Важно:** «плечо-сетинг» ≠ «эффективное плечо». Если позиция мастера в минусе, его эквити
  просело и эфф. плечо (ноционал/эквити) уезжает ВЫШЕ его сетинга. Использование маржи у нас
  = эфф_плечо ÷ плечо_сетинг (у мастера 5.73/3 = 187%, у нас 1.41/3 = 47%).

## 3. Реконсиляция — когда и чем запускается

| Триггер | Режим | Задержка |
|---|---|---|
| WS-филл цели (на HL) | `data_mode=ws` | +1.2с дебаунс (батчим серию) |
| Фолбэк-реконсиляция | `ws` | каждые 60с (страховка) |
| После обрыва WS (`on_reconnect`) | `ws` | сразу (догон пропусков) |
| Таймер опроса | `data_mode=poll` | `poll_interval_sec` (30с) |

На каждом тике: тянем стейт цели (HL) + наш (Binance) → `compute_plan` (желаемое) →
`build_orders` (diff) → `apply` (маркет-ордера). Подробный бюджет задержки (~5.7с с домашнего
Pi) — в [PIPELINE-ANALYSIS.md](PIPELINE-ANALYSIS.md).

**Идемпотентность:** пропущенный филл не теряется — следующий тик увидит расхождение позиции
и догонит. Поэтому ручная правка нашей позиции на Binance **откатывается** реконсиляцией
к цели (by design).

## 4. Догон и скейл позиций

- **Догон входа (favorability-gate):** при ОТКРЫТИИ/ДОЛИВЕ не входим, если цена сейчас **хуже
  входа цели** (с допуском `favorability_tol_pct`, по умолч. 0.3%). LONG — цена не выше входа
  мастера; SHORT — не ниже. Выходы (сокращение/закрытие) НЕ гейтятся (риск снижаем всегда).
  Гасит «догон по уехавшей цене» при нашей задержке. Если цена вернётся в выгодную зону (или
  мастер доберёт и поднимет средний вход) — реконсиляция войдёт на следующем тике.
  Выключатель: `favorability_gate`.
- **Автоскейл:** желаемое пересчитывается каждый тик от текущих эквити. Меняется наш эквити или
  эквити/ноционал мастера → желаемое плывёт → позиция подгоняется. Специально ничего делать не надо.
- **Накопление остатка:** суб-минимальные доливы не исполняются по одному, а копятся в разнице
  «цель ↔ наша» и срабатывают, когда перевалят минимум (см. §5).

## 5. Минимумы биржи и округления (важно для дрейфа)

Binance не принимает ордера мельче `minNotional` (напр. $5–$20) и `minQty`/`stepSize`.
Логика (`_resolve_qty`, churn-free под реконсиляцию):

| Случай | Поведение |
|---|---|
| **Полное закрытие** (цель→0) | всегда исполняем (reduceOnly минимум не блокирует) |
| **Открытие** суб-минимальной позиции | `min_notional_roundup=true` → **round-up** до `minNotional` (иначе мелкую позицию вообще не скопировать) |
| **Долив/частичное сокращение** меньше `minNotional` | **dead-band** — не дёргаем; дельта копится и исполнится при переходе минимума |

**Почему не «просто round-up везде»:** в реконсиляции это вызвало бы дёрганье (открыли по min →
следующий тик срезал обратно → churn). Dead-band на суб-минимальных правках это исключает.

**Округление:** `round_step` округляет количество **вниз** к `stepSize`. Остаток (< шага) копится
в разнице и добирается позже. «Пыль» ниже `minQty` закрыть нельзя — остаётся (ограничение биржи).

**Следствие для мелкого счёта:** микро-движения крупного мастера масштабируются у нас в `<minNotional`
→ часть мелких подрезок откладывается (dead-band) до накопления. На медленных свингерах незаметно;
на скальперах — копировать бессмысленно (см. PIPELINE-ANALYSIS, профиль цели).

## 6. Baseline-заморозка (что делаем с УЖЕ открытыми у мастера позициями)

Когда стартуем копирование, у мастера часто уже есть открытые позиции — мы «пропустили вход».
На ПЕРВОМ тике (`baseline`) решаем, копировать ли их:

| `start_skip_open` | Поведение на старте |
|---|---|
| `profitable` (по умолч.) | заморозить позиции, которые уже в плюсе ≥ `start_skip_profit_pct` |
| `all` | заморозить ВСЕ открытые на старте (копируем только новые входы) |
| `none` / иное | не морозить — копируем текущий портфель мастера целиком |

- `start_skip_profit_pct` — порог в %. **Был 0.001 (≈заморозить всё зелёное) — поднят до 5**:
  красные и умеренно зелёные (до +5%) копируются, морозим только «ракеты» >+5%.
- Заморозка **липкая**: решение принимается на baseline и держится, пока мастер сам не закроет
  позицию (тогда размораживается). На лету не пересчитывается — сбрасывается только рестартом
  (свежий baseline на текущем состоянии).
- Реальный кейс: pension ETH-шорт был +0.8% на старте → заморозился при пороге 0.001 → копировали
  ноль; рестарт при красном шорте → не заморозился → скопировали.

## 7. Устойчивость исполнения

- **Ретраи Binance:** транзиентные ошибки (429/418/5xx, коды -1003/-1001/-1007, сетевые сбросы)
  → до 3 повторов с экспон. бэкоффом и учётом `Retry-After`. `-1021` (рассинхрон часов) → ресинк
  и повтор. Постоянные (`-2019` маржа, `-1013` фильтр, `-4xxx`) → сразу ошибка, без ретрая.
- **Устойчивый WS:** SDK Hyperliquid сам не переподключается — наш `FillStream` следит за живостью
  (поток жив + свежесть сообщений, ловит half-open), пересоздаёт коннект + ре-подписку с backoff,
  `on_reconnect` дёргает догон. Дедуп филлов по `tid`, снимок при подписке проглатывается.
- **Hedge / one-way:** поддержаны оба режима аккаунта Binance (ведём ногу LONG/SHORT либо net-позицию).

## 8. Алерты по копии (Telegram)
Развёрнутый формат + **источник действия**:
```
📋 Скопировано · pension-usdt
🔴 ETH SHORT · ➖ Сокращение
• Размер: -0.455 → -0.441 (-3.1%)
• Ордер: BUY 0.014 (~$25) @ $1,818
• Наша позиция: ~$802 (1.41× эквити)
• Нога: SHORT
🔄 Источник: реконсиляция (бот синхронизировал позицию)
```
- `🎯 Источник: сделка трейдера` — мастер реально двигал позицию (определяется по факту: изменилась
  ли его net-позиция на этом тике).
- `🔄 Источник: реконсиляция` — бот сам свёл позицию к цели (поддержание кэпа / откат ручной правки /
  догон), мастер при этом не двигал.

Куцая строка остаётся только в UI-логе/тостах; в Telegram — развёрнуто.

## 9. Справочник настроек (`config/config.json`)

| Ключ | Назначение | Типичное |
|---|---|---|
| `targets[]` | цели: `{address, label, weight}` | 1 цель, weight 1.0 |
| `data_mode` | `ws` (push, мгновенно) / `poll` | `ws` |
| `poll_interval_sec` | период опроса в poll-режиме | 30 |
| `leverage_mode` | `mirror` / `fixed` | `mirror` |
| `mirror_max_leverage` | потолок зеркалируемого плеча | 100 |
| `fixed_leverage` | плечо в fixed-режиме | 5 |
| `leverage_cap` | потолок суммарного ноционала = эквити×cap | 3 |
| `max_notional_per_coin_usd` | потолок размера позиции по монете, $ | 800 |
| `coin_whitelist` | список монет (пусто = все) | [] |
| `start_skip_open` | заморозка на старте: `profitable`/`all`/`none` | `profitable` |
| `start_skip_profit_pct` | порог заморозки прибыльных, % | 5 |
| `favorability_gate` | не догонять по плохой цене (открытие/долив) | true |
| `favorability_tol_pct` | допуск favorability, % | 0.3 |
| `min_notional_roundup` | round-up суб-минимального открытия до minNotional | true |
| `monitor_interval_sec` | период опроса монитора (UI + backstop) | 30 |
| `monitor_min_delta_pct` | порог backstop-алерта монитора, % | 5 |
| `telegram` | `{enabled, chat_id}` (+токен в .env) | — |
| `binance.network` | `mainnet` / `testnet` | mainnet |

Боевые `config/config.json` / `.env` / `runtime/` живут только на Pi и `deploy.sh` их НЕ трогает.

## 10. Сценарии (шпаргалка)

| Хочу | Настройки |
|---|---|
| Полный риск мастера 1:1 | `max_notional_per_coin`=большой, `leverage_cap`≥эфф.плечо, `fixed_leverage`≥эфф.плечо |
| Ограничить размер по монете | `max_notional_per_coin_usd` = желаемый потолок $ |
| Ограничить суммарное плечо | `leverage_cap` = N (портфель ≤ эквити×N) |
| Брать плечо мастера | `leverage_mode=mirror`, `mirror_max_leverage` высокий |
| Своё фикс-плечо | `leverage_mode=fixed`, `fixed_leverage=N` |
| Копировать текущий портфель мастера на старте | `start_skip_open=none` |
| Не входить в чужие убежавшие плюсы | `start_skip_open=profitable`, `start_skip_profit_pct=5` |
| Не догонять по плохой цене | `favorability_gate=true`, крутить `favorability_tol_pct` |
| Мгновенные копии | `data_mode=ws` |

## 11. Известные ограничения
- Задержка event→ордер ~5.7с с домашнего Pi (REST-цепочка + дебаунс) → скальперов не догнать.
- Мелкий счёт: микро-движения мастера уходят в dead-band до накопления.
- Favorability сравнивает Binance-mark vs HL-entry (разные площадки, базис покрывается допуском).
- «Пыль» ниже minQty не закрывается (ограничение биржи).
- Заморозка на лету не пересчитывается — только рестартом.
